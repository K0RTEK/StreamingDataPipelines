# 2. Правила обработки событий и контракт корректности

## 2.1 Как выглядит входное событие (`vkr.events.raw`)

```json
{
  "event_id": "e1f2a3b4-0000-4000-8000-000000000001",
  "produced_at": "2026-01-01T00:00:00.000Z",
  "device_id": "sensor-0001",
  "event_time": "2026-01-01T00:00:03.500Z",
  "sequence": 17,
  "type": "measurement",
  "reading": 21.75,
  "unit": "celsius"
}
```

| Поле | Тип | Что значит |
|---|---|---|
| `event_id` | string (UUIDv4) | Уникальный номер события, по нему делаю дедупликацию |
| `produced_at` | string (ISO-8601 UTC) | Когда событие сгенерировали, нужно для метрики задержки |
| `device_id` | string | По нему группирую и строю окна |
| `event_time` | string (ISO-8601 UTC) | Время события, от него считаются watermark и окна |
| `sequence` | int | Номер по порядку от устройства, по нему вижу потери и дубли |
| `type` | string | Тип события, `measurement`, `heartbeat` и так далее |
| `reading` | number | Сам измеренный показатель |
| `unit` | string | Единица измерения, `celsius`, `fahrenheit` |

## 2.2 Правила фильтрации

Событие улетает в `vkr.events.invalid`, если

1. JSON не парсится или нет обязательного поля (`event_id`, `device_id`,
   `event_time`, `reading`, `type`)
2. `type != "measurement"`
3. `reading` не число, или `NaN`, или `Inf`
4. `reading` вне допустимого диапазона `[-90, 60]` (°C)
5. `device_id` пустой

Все отброшенные события уходят в side output `vkr.events.invalid` вместе с
причиной, то есть отбрасывание всегда видно, а не происходит молча

## 2.3 Правила преобразования (`vkr.events.clean`)

1. Привожу к Цельсию, если `unit == "fahrenheit"`, то `celsius = (f - 32) * 5 / 9`
2. Округляю `reading` до 3 знаков после запятой, чтобы результат был детерминирован
3. Добавляю служебные поля, `processed_at` (время обработки по часам машины) и
   `event_time_ms` (время в epoch millis), они нужны только для метрик и на
   агрегат не влияют
4. Ключ и топология события сохраняются, `key = device_id`

## 2.4 Агрегация по окнам (`vkr.windows.result`)

- Тип окна, **tumbling**, по event-time, размер **60 секунд**, границы выровнены
  по Unix-эпохе
- Ключ, `device_id`
- Watermark, стратегия **bounded out-of-orderness = 5 секунд**
- `allowedLateness` = **10 секунд**
- Что считаю по окну, `count`, `sum(reading_celsius)`, `avg`, `min`, `max`,
  а ещё `first_sequence` и `last_sequence`

Как выглядит результат

```json
{
  "device_id": "sensor-0001",
  "window_start": "2026-01-01T00:00:00.000Z",
  "window_end": "2026-01-01T00:01:00.000Z",
  "count": 42,
  "sum_c": 913.125,
  "avg_c": 21.741,
  "min_c": 19.100,
  "max_c": 24.300,
  "first_sequence": 1,
  "last_sequence": 42
}
```

## 2.5 Контракт корректности

Контракт, это список того, что я вообще считаю **правильным результатом**

1. **Полнота**, каждое событие, что прошло фильтр, попало в агрегат своего окна
   и своего `device_id` ровно один раз
2. **Точность**, для каждой пары `(device_id, window_start)` значения `count`,
   `sum_c`, `avg_c`, `min_c`, `max_c` совпадают с независимым эталоном
3. **Уникальность**, в `vkr.windows.result` на одну пару `(device_id,
   window_start)` не больше одной финальной записи
4. **Повторы**, дубли во входном потоке (одинаковый `event_id`) на уровне
   транспорта допустимы (at-least-once), но я их **дедуплицирую**, событие
   учитывается один раз, и дубль не должен менять агрегат
5. **Опоздавшие события**,
   - если `window_end <= event_time < window_end + allowedLateness`, событие
     обновляет окно и влияет на финальный агрегат
   - если позже, уходит в `vkr.events.late` и на финальный результат
     **не влияет**, это моё принятое решение, а другие варианты, "молча
     отбрасывать" или "досчитывать", обсуждаются отдельно
6. **Момент окончательности**, окно считается **окончательным**, когда watermark
   перевалил за `window_end + allowedLateness`, а запись в приёмник зафиксирована
   завершением checkpoint (см. `04-connector-guarantees.md`), и только после этого
   запись сравнивается с эталоном

## 2.6 Уровни проверки

- **Базовый уровень (по умолчанию)**, сравниваю **финальные** значения окон
- **Дополнительный уровень (по желанию)**, промежуточные обновления окна
  проверяю на монотонность и сходимость к финальному значению, сами по себе
  промежуточные обновления это **не нарушение**

То есть в контракте зафиксировано, проверяем только окончательные значения или
ещё и промежуточные, ну и по умолчанию только окончательные

## 2.7 Воспроизводимость

Эталон повторяет ровно эти правила, те же границы окон, тот же фильтр, то же
`allowedLateness`, та же нормализация единиц и округление, а если границы окон или
правила фильтрации у job и эталона разойдутся, это дефект **стенда**, а не
конвейера, и такое надо ловить ещё на этапе 2
