# Проверка сквозной корректности потокового конвейера при управляемом внедрении отказов

Это проект ВКР, то есть стенд и инструмент, где я смотрю, как **момент внедрения
отказа** (с учётом того, на каком этапе сейчас конвейер) влияет на долю найденных
нарушений при фиксированном бюджете тестирования

## Исследовательский вопрос

Помогает ли выбор момента отказа **с учётом этапов работы конвейера** находить
больше нарушений, чем **случайное** внедрение отказов при том же бюджете
тестирования

## Гипотеза

Стратегия, что учитывает состояние конвейера (незавершённый checkpoint,
накопленное состояние окна, непрочитанные offsets, незакоммиченная транзакция
приёмника), находит больше заранее внесённых дефектов на единицу бюджета, чем
равномерно случайное внедрение отказов

## Стенд (этап 1)

Поток такой, **Kafka → Flink → Kafka**

- Kafka (KRaft) это источник и приёмник
- Flink (JobManager + TaskManager) обрабатывает события через DataStream API
- Вход воспроизводим, уникальные `event_id` и детерминированный генератор
- Эталон считается **независимо** Python-скриптом, не тем же кодом, что в job

Подробнее в [`docs/01-stand-schema.md`](docs/01-stand-schema.md)

## Что считаю корректным результатом

Контракт корректности (полнота, точность, уникальность, опоздавшие события,
момент окончательности) лежит в
[`docs/02-event-processing-rules.md`](docs/02-event-processing-rules.md)

## Метрики

| Метрика | Смысл |
|---|---|
| Доля обнаруженных дефектов | обнаруженные заранее внесённые дефекты делю на все внесённые |
| Ложные срабатывания | нарушения, что помечены как дефект, когда конвейер вообще-то корректный |
| Время обнаружения | от внедрения до того, как нарушение зафиксировали |
| Накладные расходы | доп. время и ресурсы на прогон с внедрением против baseline |
| Время восстановления | считаю отдельно от корректности данных, в контракт оно не входит |

## Планируемая структура

```
flink-pipeline-vkr/
├── docs/                 # проектные документы (этап 1)
├── docker-compose.yaml   # изолированный стенд (этап 2)
├── job/                  # Flink-приложение (Maven, Java 17)
├── producer/             # воспроизводимый генератор входного потока
├── reference/            # независимый эталон на Python
├── checker/              # сверка факт/эталон + метрики
└── faults/               # внедрение отказов (этап 3)
```

Каталоги `job/`, `producer/`, `reference/`, `checker/`, `faults/` и
`docker-compose.yaml` появятся на этапе 2, уже после согласования проекта
